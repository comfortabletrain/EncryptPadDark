# Architecture, Security, and 64-Bit Technical Analysis

This document provides a detailed technical analysis of the architectural and security differences between upstream **EncryptPad** and **EncryptPadDark**, focusing on 32-bit vs. 64-bit execution, toolchain modernization, binary size factors, and in-memory cryptographic security.

---

## 1. Upstream vs. EncryptPadDark Overview

- **Upstream EncryptPad (`v0.6.0.0`)**:
  - Windows release distributed as a **32-bit x86 (`i386`)** static binary (`PE32 executable (GUI) Intel 80386`).
  - Compiled using a custom local 32-bit MinGW 13.1.0 environment (`E:/mingw32/...`) targeting the legacy Windows C runtime (`msvcrt.dll`), paired with a manually compiled Qt 6 static build configured with minimal image formats [1, 2].
  - Release archive: `encryptpad0_6_0_0_win32.zip` (~16.7 MB compressed; ~32.9 MB stripped GUI binary, ~4.7 MB CLI binary).
- **EncryptPadDark**:
  - Windows release built natively as a **64-bit x64 (`x86_64`)** static binary (`PE32+ executable (GUI) x86-64`).
  - Automated, reproducible CI build via **GitHub Actions** using the official **MSYS2 UCRT64** toolchain, linking against Microsoft's modern Universal C Runtime (`ucrtbase.dll`), `qt6-static`, and **Botan 3** [2, 3].
  - Standalone release package (zero floating application DLLs) with native dark theme support and modern OS exploit mitigations (~23.3 MB compressed; ~45.3 MB stripped GUI binary, ~3.9 MB CLI binary).

---

## 2. Binary Size Breakdown: Why the 64-Bit GUI Binary is Larger

While our command-line executable (`encryptcli.exe`) is smaller than upstream (~3.9 MB vs. ~4.7 MB) thanks to dead-code elimination (`--gc-sections`) and cleaner UCRT linking without GUI dependencies, the GUI executable (`encryptpad.exe`) is ~45.3 MB compared to upstream's ~32.9 MB. This size difference is driven by two architectural factors:

### A. 64-Bit Pointer, Instruction, & Metadata Expansion
- **Pointers & Data Model (LLP64)**: Under the 64-bit Windows LLP64 ABI, all memory addresses, pointers (`void*`), `size_t` values, and virtual method table (`vtable`) entries expand from 4 bytes (32 bits) to 8 bytes (64 bits) [4]. Furthermore, `x86_64` machine code requires `REX` instruction prefixes (`0x40`–`0x4F`) to address 64-bit registers and extended registers (`R8`–`R15`), increasing `.text` code density by ~10%–15%.
- **Qt 6 Class Hierarchy**: Qt 6 relies heavily on deep C++ inheritance, `QMetaObject` reflection structures generated by `moc`, signal/slot dispatch tables, and property mappings. Doubling the size of all pointers and vtables across `QtCore`, `QtGui`, `QtWidgets`, `QtPrintSupport`, and `QtSvg` (plus 64-bit `.reloc` base relocation tables required for ASLR) adds approximately 25%–35% to the static footprint.
- **Mandatory x64 Exception Unwind Tables (`.pdata` & `.xdata`)**: Unlike 32-bit x86, the 64-bit Windows ABI mandates table-based Structured Exception Handling (SEH) for every non-leaf function [5]. The compiler must emit 12-byte `RUNTIME_FUNCTION` records in `.pdata` and unwind metadata in `.xdata` for the OS kernel/ntdll stack unwinder. Because the OS relies on these sections at runtime for stack walking and exception dispatch, they cannot be stripped [5].

### B. Bundled Static Image Codecs
- Upstream uses a custom-tailored Qt build that disables optional image plugins.
- MSYS2's official `mingw-w64-ucrt-x86_64-qt6-static` distribution includes comprehensive image and font format support, statically linking [3]:
  - **WebP**: `libwebp`, `libwebpdemux`, `libwebpmux`, `libsharpyuv`
  - **TIFF & Compression**: `libtiff`, `libdeflate`, `jbigkit`, `lerc`
  - **Typography & Formats**: `libpng`, `libjpeg-turbo`, `freetype`, `harfbuzz`, `brotli`, `zstd`, `pcre2`

## 3. Detailed Security Assessment: 32-Bit vs. 64-Bit

### How EncryptPad Works Internally
1. **Cryptographic Standards**: Implements OpenPGP (RFC 4880) symmetric encryption (`LibEncryptMsg`) using Botan 3 [1, 6]. Supported ciphers include AES-128/192/256, Camellia-128/192/256, Twofish, CAST5, and TripleDES in OpenPGP CFB mode, alongside SHA-1/224/256/384/512 and ZLIB/ZIP/BZIP2 compression [1].
2. **Key Derivation (S2K)**: Uses OpenPGP Iterated and Salted String-to-Key (S2K, RFC 4880 § 3.7.1.3) derivation with SHA-256 [6]. By default, the encoded S2K count is set to `1,015,808` octets hashed (encoded byte `0x9F`), configurable up to the RFC 4880 maximum of `65,011,712` octets hashed (encoded byte `0xFF`, derived via $(16 + (c \mathbin{\&} 15)) \ll ((c \gg 4) + 6)$) [6].
3. **Key Material Protection**: Passphrases and derived session keys are stored in `EncryptMsg::SafeVector` (`Botan::secure_vector<uint8_t>`) [7]. When backed by Botan's `locking_allocator`, pages are pinned in physical RAM via Windows `::VirtualLock` to prevent the OS memory manager from paging keys to the disk swapfile (`pagefile.sys`), and memory is scrubbed via `Botan::scrub_memory` (`SecureZeroMemory`) upon destruction [8].
4. **Data Streaming**: Binary file encryption streams data through a 64 KiB memory buffer (`kDefaultMemoryBuffer = 65536`), avoiding large contiguous allocations for multi-gigabyte files.
5. **The In-Memory Plaintext Model**: As documented in EncryptPad's *Known Weaknesses*, editing an encrypted text file requires loading the decrypted plaintext into process memory inside Qt's `QPlainTextEdit` / `QTextDocument` [1]. Unlike `SafeVector`, Qt's internal UTF-16 `QString` heap buffers are allocated on the standard process heap and are not pinned via `VirtualLock`. Consequently, **process-level memory protection is the primary barrier protecting decrypted text in RAM**.

### Security Domains Analysis

#### 1. Mathematical Cryptography & Ciphertext Interoperability
- **Is security compromised on 32-bit?** **No.**
- **Details**: Botan 3's implementations of AES-256, SHA-256, and OpenPGP S2K produce bit-for-bit identical mathematical output regardless of target bitness [6, 8]. Ciphertexts stored on disk have identical cryptographic strength and full interoperability between 32-bit and 64-bit builds.

#### 2. Address Space Layout Randomization (ASLR), DEP, & In-Memory Defense
- **Is security compromised on 32-bit?** **Yes (Moderate to High Risk).**
- **Details**:
  - **32-Bit Windows**: The standard user-mode virtual address space is restricted to **2 GB** (`0x00000000`–`0x7FFFFFFF`) [9]. ASLR in 32-bit processes provides only **8 bits of entropy** (256 possible base locations) for executable images and bottom-up allocations, and up to **14 bits** (16,384 locations) for DLLs and stack bases [10]. This constrained space makes memory layouts vulnerable to brute-forcing and heap spraying.
  - **64-Bit Windows (HEASLR)**: High-Entropy ASLR (`IMAGE_DLLCHARACTERISTICS_HIGH_ENTROPY_VA`) spans a **128 Terabyte** user-mode virtual address space (`0x00000000'00000000`–`0x00007FFF'FFFFFFFF`) [9]. It provides **17–19 bits of entropy** for EXE/DLL bases, **24 bits of entropy** (16.7 million regions across 1 TB of variance) for bottom-up heap allocations, and **~33 bits of combined entropy** (over 8.5 billion possible positions) for stack pointers [10, 11].
  - **Mandatory Hardware DEP**: On 64-bit Windows, Hardware Data Execution Prevention (DEP / NX bit) is mandatory and enforced unconditionally by the kernel for all 64-bit processes, whereas 32-bit processes allow DEP to be disabled via compatibility policies [11].
  - **Impact on EncryptPad**: Because decrypted text resides unencrypted in `QTextDocument` heap memory, any memory-corruption bug in a reachable parser (e.g., rich-text pasting, SVG icon rendering, font shaping in HarfBuzz/FreeType, or decompression) can exploit 32-bit low-entropy ASLR via Return-Oriented Programming (ROP) or heap spraying. 64-bit HEASLR + mandatory DEP makes blind memory exploitation virtually infeasible [10, 11].

#### 3. Stack Protection, Exception Handling, & Calling Conventions
- **Is security compromised on 32-bit?** **Yes (Moderate Risk).**
- **Details**:
  - **Calling Conventions (`i386` vs. `x86_64`)**: In 32-bit MinGW (`__cdecl` / `__stdcall`), function arguments and pointers to sensitive buffers are pushed directly onto the call stack adjacent to local buffers and return addresses. Under the 64-bit Windows ABI, the first four integer/pointer arguments are passed in hardware registers (`RCX`, `RDX`, `R8`, `R9`) and floating-point arguments in `XMM0`–`XMM3`, significantly reducing stack exposure of sensitive pointers [4].
  - **Elimination of Stack-Based SEH Overwrites**: 32-bit Windows stores Structured Exception Handling registration records (`EXCEPTION_REGISTRATION_RECORD`) as a linked list directly on the stack (`FS:[0]`), making exception handlers a classic target for stack buffer overflows. 64-bit Windows moves exception dispatch metadata out of the stack into read-only `.pdata` and `.xdata` PE sections, completely eliminating stack-based SEH hijacking [5].
  - **Hardware-Enforced Stack Protection (CET)**: Modern 64-bit Windows supports Intel Control-flow Enforcement Technology (CET) and AMD Shadow Stacks, protecting return addresses in hardware against ROP attacks [11].

#### 4. Cryptographic Timing, Register File, & Side-Channel Resistance
- **Is security compromised on 32-bit?** **Low to Moderate Risk.**
- **Details**:
  - **Native 64-Bit Arithmetic vs. Multi-Instruction Emulation**: 64-bit cryptographic algorithms (such as SHA-512, 64-bit block counters, and Botan's `CT::Mask<uint64_t>` constant-time multiplexers) execute as single-cycle hardware instructions on `x86_64`. On 32-bit `i386`, 64-bit operations must be synthesized using paired 32-bit instructions with carry-flag propagation (`add`/`adc`, `shld`/`shrd`) or compiler runtime helpers (`__muldi3`/`__allmul`). Academic research has demonstrated that compilers frequently optimize 64-bit synthesized arithmetic on 32-bit targets into secret-dependent conditional branches, breaking constant-time guarantees [12, 13].
  - **CPU Register Starvation & Stack Spilling**: 32-bit `i386` provides only **8 general-purpose registers** (6 usable outside `ESP`/`EBP`) and **8 XMM registers** (`XMM0`–`XMM7`). 64-bit `x86_64` doubles this to **16 general-purpose 64-bit registers** (`RAX`–`R15`) and **16 XMM registers** (`XMM0`–`XMM15`) [4]. On 32-bit builds, high register pressure forces the compiler to spill intermediate cipher state and round keys onto the stack (L1 cache/RAM), introducing cache-timing side channels and leaving residual key material in un-zeroed stack frames.

#### 5. C Runtime Modernization & Large File Stability
- **Is stability/security compromised on 32-bit?** **Yes (Low to Moderate Risk).**
- **Details**:
  - **Modern UCRT vs. Legacy MSVCRT**: `EncryptPadDark` links against Windows 10/11's Universal C Runtime (`ucrtbase.dll`), which receives active security hardening from Microsoft, whereas 32-bit MinGW builds typically rely on the legacy `msvcrt.dll` runtime [2].
  - **Elimination of 2 GB Address Space Exhaustion**: Decompressing large archives (e.g., `bzip2` streams) or editing large documents inside a 2 GB 32-bit address space can trigger out-of-memory (`std::bad_alloc`) crashes due to virtual address space fragmentation—an issue noted in upstream's own `v0.6.0.0` release history [1]. Native 64-bit addressing removes this ceiling entirely.

## 4. Security Risk Matrix

| Security Area | 32-Bit Legacy Build (`i386`) | Native 64-Bit Build (`x86_64`) | Real-World Risk on 32-Bit? |
| :--- | :--- | :--- | :--- |
| **Cipher & Hash Integrity** | Identical (RFC 4880) | Identical (RFC 4880) | **None** (identical mathematics) |
| **ASLR Entropy** | 8–14 bits (2 GB space) | 17–33+ bits (128 TB space) | **High** (brute-forceable memory layout) |
| **Hardware DEP (NX)** | Optional / Can be disabled | Mandatory & unconditional | **Moderate** |
| **In-Memory Plaintext Defense** | Vulnerable to ROP / heap spraying | Strong (HEASLR + DEP + CET) | **Moderate to High** |
| **Exception Handling (SEH)** | Stack-based (`FS:[0]` overwritable) | Table-based (read-only `.pdata`/`.xdata`) | **Moderate** |
| **Calling Convention & Registers** | Stack args; 8 GPRs / 8 XMM (spills to RAM) | Register args (`RCX`–`R9`); 16 GPRs / 16 XMM | **Moderate** |
| **Constant-Time Crypto Timing** | Emulated 64-bit ops (`add`/`adc` chains) | Native 64-bit ALU instructions | **Low to Moderate** |
| **C Runtime & Memory Ceiling** | Legacy `msvcrt.dll`; 2 GB OOM ceiling | Modern `ucrtbase.dll`; 128 TB ceiling | **Low to Moderate** |

---

## 5. Conclusion

Building a 32-bit binary produces encrypted files that are cryptographically identical on disk. However, because EncryptPad's primary runtime function involves holding decrypted secrets and plaintext documents in volatile RAM, a **native 64-bit architecture (`EncryptPadDark`) provides critical defense-in-depth**: combining High-Entropy ASLR, mandatory DEP, table-based non-stack exception handling, doubled CPU register capacity, and native 64-bit constant-time execution to protect process memory against local extraction and memory-corruption exploits.
